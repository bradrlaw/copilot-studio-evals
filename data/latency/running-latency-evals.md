# Running the Banking Tool Latency Evaluations

How to run the [banking latency dataset](./banking_latency_eval.jsonl) through the
**Copilot Studio built-in evaluation** tool and then extract the **actual**
per-tool latency to compare against each query's `expected_latency_ms`.

> 📝 **Note:** The built-in evaluation tool measures *response quality*, not tool
> latency. It is used here only as a convenient, repeatable way to **drive** the
> 50 synthetic banking utterances at the agent. The latency numbers come from **telemetry**
> (App Insights), not from the evaluation report itself.

---

## 1. The import files (one per tool)

Generated by
`../../scripts/convert_jsonl_to_copilot_csv.py ... --split-by tool`:

| File | Tool | Conversations | Illustrative p95 target (ms) |
| --- | --- | :---: | :---: |
| `banking_latency_copilot_account_balance.csv` | `account.balance` | 12 | 2000 ms |
| `banking_latency_copilot_transaction_search.csv` | `transaction.search` | 12 | 3000 ms |
| `banking_latency_copilot_payee_search.csv` | `payee.search` | 8 | 2000 ms |
| `banking_latency_copilot_card_list.csv` | `card.list` | 8 | 2000 ms |
| `banking_latency_copilot_transfer_validate.csv` | `transfer.validate` | 5 | 2500 ms |
| `banking_latency_copilot_payment_validate.csv` | `payment.validate` | 5 | 2500 ms |

Each row is a **single-turn conversation** (one banking request → one tool call),
so N conversations = N tool calls. Columns are the Copilot Studio template
(`conversationNumber, question, response`); `response` is intentionally blank
(the tool ignores it).

> 💡 **Tip — why one file per tool:** Importing and running **one file at a time**
> means every tool call in that run is the *same* banking tool inside one narrow
> time window. That is what makes the "tool latency report for the time range"
> approach below actually isolatable — you don't have to untangle multiple tools from
> one blended window. Run the files sequentially, not all at once.

Regenerate all six:

```powershell
python ../../scripts/convert_jsonl_to_copilot_csv.py `
  banking_latency_eval.jsonl banking_latency_copilot.csv --split-by tool
```

---

## 2. Run each file in Copilot Studio (and record the window)

For **each** of the six CSVs, one at a time:

1. Copilot Studio → open the **agent under test** in the test environment →
   **Test your agent** panel → **⋯ / Evaluate** → **Import conversations**.
2. Upload one per-tool CSV and start the run.
3. **Record the wall-clock window** — this is the single most important step for
   isolating latency afterwards:
   - **Start** = UTC time just before you click Run.
   - **End** = UTC time when the run finishes.
   - Add a small buffer (±30 s) on each side.
4. Let the run finish completely before importing the next tool's file, so the
   windows don't overlap. Note the tool name against each window.

Keep a scratch table like this while you run:

| Tool | Run start (UTC) | Run end (UTC) |
| --- | --- | --- |
| account.balance | `<START_TIME_UTC>` | `<END_TIME_UTC>` |
| transaction.search | ... | ... |
| payee.search | ... | ... |
| card.list | ... | ... |
| transfer.validate | ... | ... |
| payment.validate | ... | ... |

> ⚠️ **Warning — shared-environment noise:** App Insights may also receive traffic
> from other testers. Running one tool per tight window plus filtering on the tool
> name (below) removes almost all of it, but for the cleanest numbers run during
> a quiet period.

## 3. Option A — Tool latency report scoped to the run window (recommended)

This reuses observability **Query 3** (`../../telemetry/queries/genai_observability_queries.kql`),
but bounded to the run window and filtered to the one tool. Paste each tool's
`start`/`end` from the table above.

```kusto
// Windowed tool-latency report — run once per tool.
// Set these three to match the run you are analysing:
let winStart = datetime(<START_TIME_UTC>);
let winEnd   = datetime(<END_TIME_UTC>);
let toolFilter = "<CANONICAL_TOOL_NAME>";
dependencies
| where timestamp between (winStart .. winEnd)
| extend cd = customDimensions
| extend genaiTool = tostring(cd["gen_ai.tool.name"]),
         mcpTool   = tostring(cd["mcp.tool.name"])
| where isnotempty(genaiTool) or isnotempty(mcpTool)
        or name in ("ExecuteTool", "mcp.tool")
        or tostring(cd["gen_ai.operation.name"]) == "execute_tool"
| extend toolName = iif(isnotempty(genaiTool), genaiTool,
                    iif(isnotempty(mcpTool), mcpTool, name))
| where toolName == toolFilter
| summarize calls   = count(),
            failed  = countif(success == false),
            p50Ms   = round(percentile(duration, 50), 1),
            p95Ms   = round(percentile(duration, 95), 1),
            maxMs   = round(max(duration), 1)
        by toolName
```

Compare the returned `p95Ms` to the `expected_latency_ms` for that tool.
**Pass** = `p95Ms <= expected_latency_ms` **and** `failed == 0`.

Want per-call rows instead of an aggregate (to see individual outliers and match
them to specific utterances by timestamp order)? Replace the final `summarize`
with:

```kusto
| where toolName == toolFilter
| project timestamp, toolName, durationMs = duration, success, resultCode
| order by timestamp asc
```

`calls` should equal the row count of the file you ran. If it
is lower, some utterances didn't trigger the tool (agent asked a clarifying
question or refused) — check the transcript for those.

### Run it from the CLI
You can pull the same numbers without the portal using the repo helper. It
selects a numbered `// QUERY <id>:` block from a `.kql` file, so add the windowed
KQL above as a block (e.g. `// QUERY 3w: windowed tool latency`) in a scratch
`.kql` file, then:

```powershell
python ../../scripts/run_kql_query.py `
  --app-id <APP_INSIGHTS_APPLICATION_ID> `
  --api-key <APP_INSIGHTS_API_KEY> `
  --kql-file windowed_latency.kql --query 3w --output banking_tool_latency.csv
```

Edit the `winStart` / `winEnd` / `toolFilter` `let` lines in that block for each
tool before re-running. Don't commit the API key or the scratch file.

## 4. Option B — Manual, from the Copilot Studio portal

If you can't (or don't want to) query App Insights:

1. Copilot Studio → agent → **Analytics** → **Sessions/Transcripts**, or open the
   evaluation run's per-conversation results.
2. Open each conversation from the run and read the response time shown for the
   turn.

> ⚠️ **Warning — this is a coarser proxy.** The portal surfaces **end-to-end
> message response time** (model + orchestration + tool round-trip), *not* the
> isolated tool-call `duration`. It is fine for a quick "is anything wildly over
> target" sniff test, but the recorded baseline should use **Option A**, whose
> `duration` matches how the `expected_latency_ms` thresholds were derived
> (observability Query 3 `p95`).

---

## 5. Record the result

Summarise per tool: `calls`, `p95Ms`, `expected_latency_ms`, pass/fail, and any
outlier utterances. Attach that table (plus the run-window table from Step 2) to
the eval task as the measured latency baseline. Mark thresholds as provisional when they are estimates rather than
approved service objectives or measured baselines; see the dataset
[README](./README.md).
